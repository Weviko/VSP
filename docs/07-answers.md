### Q34 답변의 결정적 부연 (사용자 원문)
> "베트남 체육회와 직접 논의할 수 있는 부문이라 이에 대한 공식 서류 폼을 나중에 받아서
> 베트남 중앙의 체육회에서 나머지 협회에 **지정 폼으로서 강제**할 수 있음."

**이것이 사업 구조를 바꾼다 (Top-Down 강제 모델)**

일반적인 스포츠 SaaS는 협회마다 다른 업무 방식에 시스템을 맞춰야 해서 전 종목 일괄이 실패한다.
그러나 **중앙 체육회가 표준 서식을 강제할 수 있다면, 우리는 협회에 맞추는 것이 아니라 표준을 협회에 배포하는 입장**이 된다.

| 항목 | 일반적 SaaS (Bottom-Up) | **우리 (Top-Down 강제)** |
|---|---|---|
| 서식 | 협회마다 다름 → 커스터마이징 지옥 | **중앙 표준 폼 1종 + 종목별 확장 필드** |
| 온보딩 | 협회를 설득해야 함 | 중앙이 공문으로 지시 |
| 개발 범위 | 협회 수 × 요구사항 | 표준 1벌 |
| 최대 위험 | 협회가 안 씀 | **표준 폼 확정이 늦어지면 전체가 멈춤** |

**따라서 최우선 과제가 바뀐다: "공식 서류 폼 실물 확보"가 개발 착수의 전제조건이다.**

### 전 종목 일괄에서 반드시 지켜야 할 구분
- **기술 릴리스(전 종목 동시)** 와 **조직 온보딩(순차)** 을 분리한다.
- 시스템은 처음부터 전 종목을 담되, 실제 협회 투입은 3~5개씩 웨이브로 나눈다.
- 이유: 동시 온보딩 시 헬프데스크가 마비되고 첫인상이 무너진다. 시스템 범위와 롤아웃 속도는 다른 문제다.

## ⚠️ 이 전략의 최대 위험과 대응 — 반드시 지킬 아키텍처 원칙

**위험**: 공식 서류 폼(표준 서식)을 **아직 받지 못한 상태에서** 본격 개발을 시작한다.
나중에 체육회가 준 서식과 우리가 만든 화면·DB가 안 맞으면 **대규모 재작업**이 발생한다.
이것이 이 전략의 유일하고 치명적인 약점이다.

**대응 — 하드코딩 금지 원칙 (Configuration over Code)**

| 하드코딩하면 죽는 것 | 반드시 "데이터/설정"으로 만들 것 |
|---|---|
| 신청서 항목 | **동적 폼 스키마 엔진** — 필드 정의가 DB에 저장되고 화면이 그것을 렌더링 |
| 결재선(승인 단계) | **워크플로 엔진** — 단계·승인자·조건을 데이터로 정의 |
| 종목/세부종목/부문 | 종목 테이블 (코드 수정 없이 추가) |
| 등록비·참가비 규칙 | 요금 규칙 엔진 |
| 문서 서식·출력물 | 템플릿 엔진 (PDF 레이아웃도 데이터) |
| 화면 문구 | i18n 리소스 (vi/en/ko) |

> **효과**: 체육회가 나중에 "이 칸을 추가하고 결재를 3단계로 바꿔라"고 해도 **코드 수정 없이 관리자 화면에서 설정 변경**으로 끝난다.
> 이것이 "먼저 만들고 나중에 베트남 실정에 맞춘다"는 전략을 성립시키는 **유일한 방법**이다.
> 초기 개발이 20~30% 느려지지만, 이걸 안 하면 서식 수령 시점에 프로젝트가 반쯤 무너진다.

**두 번째 대응**: 서식을 못 받은 지금도 **확실히 아는 것부터** 만든다.
조직 계층 · 통합 ID · 권한 · 인증 · 감사로그 · 결제 연동 · 미디어 페이지 —
이것들은 서식과 무관하며 전체 공수의 절반 이상이다. 서식 의존 화면은 엔진 위에 나중에 얹는다.

**세 번째: "완성도를 어디까지"의 기준**
자본 소진을 막기 위해 목표를 명시한다 →
**"협회 1곳이 선수 등록부터 대회 결과 공개까지 실제로 운영할 수 있는 상태"**. 그 이상은 투자 유치 후.

| 과거 대회·선수 기록은 옛 63개 성 기준 | **구-신 지역 매핑 테이블** 필요. 과거 성적을 조회할 때 옛 지명으로도 검색되어야 함 |
| 선수의 소속 지역이 바뀜 (본인 의사와 무관하게) | 이적(transfer)과 **행정구역 개편에 의한 소속 변경**을 구분해서 기록 |

> 이 사실을 모르고 설계했다면 지역 코드를 63개로 고정해 넣었을 것이고, 데이터 전체를 다시 만들어야 했다.
> **오히려 지금이 최적의 시점이다** — 개편 직후라 새 체계로 깨끗하게 시작할 수 있다.

> 새로 개발하는 게 아닌, 먼저 개발 이후에 **쉽게 붙일 수 있게** 진행해줘.

**→ 설계 결론: 전략 패턴 + 생성기 레지스트리**

대진 생성 로직을 `if (format === 'TOURNAMENT') ... else if ...` 로 쓰면 방식을 추가할 때마다
기존 코드를 뜯어야 한다. 대신 **생성기 인터페이스를 정의하고 레지스트리에 등록**하는 구조로 간다.

```
BracketGenerator (인터페이스)
  ├─ SingleEliminationGenerator   ← 지금 구현
  ├─ RoundRobinGenerator          ← 지금 구현
  ├─ GroupKnockoutGenerator       ← 나중에 파일 하나 추가 + register() 한 줄
  ├─ MeasuredEventGenerator       ← 나중에 (수영/육상 레인 배정)
  └─ ScoredEventGenerator         ← 나중에 (체조/다이빙 연기 순서)
```
새 방식을 추가할 때 **기존 파일은 단 한 줄도 수정하지 않는다.** 파일을 만들고 등록만 하면 된다.

|---|---|

| 증명서 발급 + **검증** | 발급 + 진위확인(로그인 불필요) 구현 |
| 대회일정 주간/월간/연간 | 3단 보기 구현 |
| 내 생애주기 | '내 업무'로 메뉴 확보 |
| 준회원 제도 | 조직 상태로 대응 가능 (신규 종목 흡수) |

## 14차 (2026-09-11) — 부처 레벨 확장 방침

| 질문 | **확정 답변** |
|---|---|
| 이식 범위 | **한국 문체부의 행정·운영 시스템을 그대로 이식** (체육회 레벨 → 부처 레벨) |
| 본 제작 착수 순서 | **설정 도구 먼저** — 서식 편집기 · 결재선 편집기 |
| 문서 범위 표시 | **수정한다** — 체육회 레벨 완료 / 부처 레벨 예정으로 구분 |
| 베트남 정부 기존 시스템 | **없다고 가정하고 만들되, 연동 여지를 남긴다** |

### 착수 순서를 '설정 도구'로 정한 이유
서식·결재선 엔진은 만들었으나 **조작할 화면이 없다.** 체육회 서식을 받아도
개발자가 SQL로 넣어야 하는 상태이며, 그러면 "협의 피드백을 설정 변경으로 흡수한다"는
전략이 성립하지 않는다. 미팅에서 "이 칸 추가해주세요"에 **"관리자 화면에서 바로 됩니다"**로
답할 수 있어야 한다.

### 기존 시스템 가정에 대한 설계 대응
베트남에 온나라·e나라도움에 해당하는 시스템이 있는지 확인되지 않았다.
**없다고 가정해 자체 구현하되**, 외부 시스템과 주고받을 수 있도록
공문·보조금 모듈에 **연계 인터페이스(외부 문서번호·외부 사업코드 필드와 송수신 훅)**를 남긴다.
나중에 연동이 필요해지면 어댑터만 붙이면 된다.
