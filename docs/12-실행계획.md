# 12. 실행 계획 — 본 제작을 어떻게 진행할 것인가

> 작성일 2026-09-11 · 대상: 사업 주체, IT팀, 문체부 협의 담당
> 선행 문서: 10(사업계획서) · 11(갭 분석)

---

## 0. 이 문서가 답하는 질문

"구조가 끝났으니 이제 본격적으로 만들자"에서 **무엇을, 어떤 순서로, 누가, 언제**를 정한다.
동시에 **지금 만들면 안 되는 것**도 명시한다. 그것이 이 계획의 핵심이다.

## 2. 진행 전 반드시 짚어야 할 세 가지

### 2-1. 1순위에 구멍이 두 개 남아 있다

| # | 빠진 것 | 왜 1순위인가 |
|---|---|---|
| **D2** | **결재선 편집기(GUI)** | 서식 편집기는 만들었는데 **결재선은 아직 SQL로만 바꿀 수 있다.** 종목마다 승인 단계가 다른데, 문체부가 "이 종목은 3단계"라고 하면 개발자를 불러야 한다. "설정으로 대응한다"는 전략이 절반만 성립한다 |
| **D7** | **PDF 출력** | 교부 결정문·증명서·공문을 **출력할 수 없다.** 베트남 행정은 여전히 종이 원본을 요구하는 절차가 많고, 결정문에 서명·날인이 필요하다 |

이 둘은 **문체부가 무슨 말을 하든 반드시 필요하다.** 미팅 결과와 무관하므로 지금 만드는 것이 맞다.

### 2-2. 공식 서식이 아직 한 장도 오지 않았다

`docs/received/` 가 비어 있다. 문서 08에서 정한 **1차 요청 3종**(선수등록·대회개최·사업계획)이 아직 전달되지 않았다.

이것이 이 사업 전체의 **1번 병목**이다. 이유:

- 지금 화면에 있는 등록 서식은 **한국 서식을 참고해 우리가 추정한 것**이다. 실제와 다르면 시연에서 바로 지적당한다
- 반대로, **미팅 전에 서식이 도착하면** 문체부 담당자가 자기가 쓰는 그 서식을 화면에서 보게 된다. 설득력이 완전히 달라진다
- 서식 반영에 드는 시간은 **서식 편집기로 한 건당 1~2시간**이다. 개발 일정이 아니라 **수령 일정**이 전부다

> **권고: 미팅 일정을 잡는 연락에 서식 요청을 같이 붙인다.** 별도로 요청하면 한 번 더 기다려야 한다.

### 2-3. "한국 부처 시스템 이식"의 전제가 아직 확인되지 않았다

우리는 온나라시스템(공문 유통)과 e나라도움(보조금)을 이식하는 설계를 해 두었다. 그런데:

- **베트남에 이미 국가 전자문서시스템이 있다면** → 우리는 만드는 게 아니라 **연동**해야 한다
- **국가 보조금 관리 시스템이 있다면** → 마찬가지다

둘 중 하나라도 이미 있는데 우리가 따로 만들면, 부처는 **두 시스템에 같은 공문을 두 번 넣어야 한다.** 그 순간 시스템은 버려진다.

> 이 두 질문은 미팅 **첫 30분 안에** 확인해야 한다. 설계가 갈리는 지점이기 때문이다.
>
> **2026-09-14 확인 (문서 13 §3)**: 공개 자료상 **국가기관 층에는 이미 있다** — 국가 공문 유통 축(95개 기관), 국가 공공서비스 포털(VNeID 로그인), 국가 보고 시스템.
> 대회 개최 신청도 이미 국가 행정절차다. 다만 **국가 종목연맹은 국가기관이 아닌 사회·직능 단체**라 이 축에 없다.
> → VSP는 **체육단체 층**을 만들고 경계에서 국가 시스템과 잇는다. 미팅에서는 "있는가"가 아니라 "**어떻게 잇는가**"를 묻는다.

## 3. 진행 원칙 — 남은 일을 두 무더기로 나눈다

지금 모든 것을 다 만들면 안 된다. **문체부 의견에 따라 버려질 수 있는 것**이 있기 때문이다.
그래서 남은 작업을 다음 기준으로 나눈다.

| 구분 | 정의 | 지금 할 것인가 |
|---|---|---|
| **결정 무관** | 문체부가 무슨 말을 하든 필요한 것 | **지금 전속력으로** |
| **결정 의존** | 부처 요구에 따라 범위·형태가 바뀌는 것 | **미팅 후에** |

### 3-1. 결정 무관 — 지금 만든다

| # | 작업 | 근거 |
|---|---|---|
| 1 | **결재선 편집기(GUI)** | 결재선이 어떤 모양이든 편집기는 필요 |
| 2 | **PDF 출력** (결정문·증명서·공문·명단) | 출력은 어느 기관이든 요구 |
| 3 | **권한 관리 화면 + 조직 범위 권한** | 역할·권한 부여는 모든 조직에 공통. **지금은 "업무 역할이 있는가"까지만 확인한다 — A 협회 직원이 B 협회 수납을 기록하는 것이 아직 막히지 않는다** (문서 13 §7-1) |
| 4 | **종목·세부종목 관리 화면** | 종목 분류표가 오면 화면으로 넣어야 함 |
| 5 | **감사로그 조회 화면** | 감사 대응은 정부 시스템의 기본 요건 |
| 6 | **엑셀 일괄 업로드(데이터 이관)** | 기존 수기 명단을 옮기는 유일한 현실적 수단 |
| 7 | **첨부 화면 연결** (조직·행사·보조금 문서함) | 업로드 기능은 됐으나 붙일 자리가 아직 일부만 있음 |
| 8 | **빈 화면 8면 채우기** (뉴스·공지·랭킹·내업무·보고서 등) | 시연 중 빈 화면이 나오면 신뢰를 잃음 |
| 9 | **베트남어 문구 원어민 검수** | 지금 문구는 기계적 번역 수준. 정부 대상 시연에서 어색한 관공서 용어는 치명적 |
| 10 | **시연 시나리오 + 시연용 데이터** | 미팅의 실제 산출물 |
| 11 | **운영 기본기** (세션 보안·요청 제한·백업/복구 절차) | 정부 시스템 지정 심사 항목 |

### 3-2. 결정 의존 — 미팅 전에는 손대지 않는다

| # | 작업 | 무엇에 따라 갈리는가 |
|---|---|---|
| 1 | 공문 유통 세부 | 국가 전자문서시스템 존재 여부 → 자체 구축 vs 연동 |
| 2 | 보조금 세부 | 국가 보조금 시스템 존재 여부 |
| 3 | 위원회·감사·도핑·징계 | 부처가 원하는 범위 |
| 4 | 국가대표·심판 배정 | 체육회 본업 편입 여부 |
| 5 | 장애인체육 | 같은 플랫폼 vs 분리 |
| 6 | 결제 실연동 | PG 선정(VNPAY/MoMo) 및 계약 |
| 7 | 전자서명·VNeID | 정부 승인 및 기관 인증 절차 |
| 8 | 오픈 API | 대외 공개 정책 |

> **"안 쓸 기능을 미리 만드는 것이 이 사업에서 가장 큰 낭비다."** (문서 11 §4)

## 4. 단계별 계획

| 단계 | 목표 | 완료 기준 | 기간(안) |
|---|---|---|---|
| **P0** | 미팅 준비 완결 | 시연 가능한 베트남어 시스템 + 요청 서식 발송 | 3~4주 |
| **P1** | 문체부 미팅 | 12개 확인 질문 답변 확보 + 서식 수령 | 1주 |
| **P2** | 구조 확정 · IT팀 합류 | 요구사항 반영 + 디자인 시스템 적용 | 6~10주 |
| **P3** | 파일럿 (1~2개 종목) | 실제 등록·대회 1사이클 완주 | 8~12주 |
| **P4** | 전국 확산 | 전 종목 온보딩 | 6~12개월 |
| **P5** | 공개 플랫폼 | 미디어·랭킹·후원 중개 | P3와 병행 시작 |

기간은 **안(案)**이다. P1의 답변에 따라 P2 이후는 크게 달라진다.

### P0 — 미팅 준비 완결 (지금~3~4주)

3-1의 11개 항목을 전부 끝낸다. 이 단계의 산출물은 기능이 아니라 **"미팅에서 보여줄 수 있는 상태"**다.

**시연 시나리오(권장 순서, 약 20분):**

1. 협회 담당자가 **선수 등록 신청** — 첨부 포함
2. 상급 단체에서 **결재 2단계 승인** — 법정 처리기한 표시
3. 승인 즉시 **공개 선수 검색**에 반영 (만 18세 미만은 비공개인 것도 같이 보여줌)
4. **대회 개최 신청** → 10일 법정기한 카운트 → 승인 → 대진 자동 생성
5. **보조금 공모 → 교부 → 집행 → 정산 → 검사 → 공시** (가장 중요. 부처의 관심사)
6. **부정 차단 시연** — 교부액 초과 집행, 증빙 중복 제출이 실제로 막히는 것을 보여줌
7. **엑셀 내보내기**로 감사 자료 즉시 출력
8. **서식 편집기** — 그 자리에서 항목 하나 추가 → 화면에 즉시 반영

> 8번이 이 시연의 승부처다. "요구사항이 바뀌면 얼마나 걸리냐"는 질문에
> **그 자리에서 바꿔 보이는 것**이 어떤 설명보다 강하다.

### P1 — 문체부 미팅

문서 11 §5의 12개 질문을 확인한다. 그중 **설계가 갈리는 것 4개**를 최우선으로:

1. 국가 전자문서시스템이 있는가
2. 국가 보조금 관리 시스템이 있는가
3. 체육 예산이 어느 경로로 협회에 내려가는가
4. 장애인체육을 같은 플랫폼에 담는가

**동시에 받아야 할 것:** 1차 서식 3종, 34개 성/시 코드표, 국가 종목연맹 명단, 체육회 조직도.

**국가 시스템 연동 질문 (문서 13 §7-2):** 대회 개최 행정절차와 VSP 대회 승인의 관계 · 문체부 문서관리시스템 연동 · VNeID 로그인 · 보고 시스템 양식 · 대외 웹사이트 운영 주체와 도메인.

### P2 — 구조 확정 및 IT팀 합류

- 미팅 의견을 **설정으로 흡수**(서식·결재선·권한) — 코드 변경 없이
- 코드 변경이 필요한 것만 별도 목록화 → 우선순위 재산정
- **디자인 시스템 적용** — 지금 화면은 의도적으로 최소 스타일이다. 여기서 브랜딩·타이포·컴포넌트를 입힌다
- 결정 의존 기능 중 부처가 실제로 원한 것부터 착수

### P3 — 파일럿

**전 종목을 한꺼번에 올리지 않는다.** 1~2개 종목으로 한 사이클을 완주한다.

- 권장: **회원 수가 많고 행정이 정돈된 종목 1개 + 규모가 작은 종목 1개**
- 큰 종목은 부하와 예외 상황을 드러내고, 작은 종목은 온보딩 난이도를 보여준다
- 완주 기준: 등록 → 대회 개최 → 참가 → 결과 → 정산까지 **실제 데이터로** 한 바퀴

> 상향식 확산이 아니라 **하향식 강제**가 가능한 구조(중앙이 표준 서식을 지정)이므로,
> 파일럿의 목적은 "쓸지 말지 설득"이 아니라 **"결함을 실제 업무에서 찾아내는 것"**이다.

### P4 — 전국 확산

종목별 순차 온보딩. 각 종목마다 필요한 것은 개발이 아니라 **기준 데이터 + 교육**이다.

### P5 — 공개 플랫폼

기록·랭킹·뉴스·선수 프로필. 행정 데이터가 쌓여야 의미가 생기므로 P3와 겹쳐 시작한다.
**후원 중개는 선수 프로필 데이터가 충분히 쌓인 뒤**에 연다.

추가로 만들어야 할 것:
- 화면별 기능 명세(스크린샷 포함)

- 개발 규칙 문서(브랜치, 리뷰, 배포)

## 6. 인프라 전환 계획

현재는 **PGlite**(인프로세스 PostgreSQL)로 개발 중이다. 설치가 필요 없어 빠르지만, 한 프로세스만 파일을 열 수 있어 여러 명이 동시에 못 쓴다.

| 시점 | 환경 | 비고 |
|---|---|---|
| 지금 | PGlite (`pglite://.pgdata`) | 1인 개발 |
| **IT팀 합류 즉시** | PostgreSQL (NAS 또는 개발 서버) | `DATABASE_URL` 한 줄만 바꾸면 됨 |
| 파일럿 | 베트남 내 서버 | 아래 데이터 위치 항목 참조 |
| 운영 | 이중화 + 백업 | |

**설계상 이 전환에 코드 변경이 없다.** 드라이버 추상화와 `file://` / `s3://` 저장소 추상화를 처음부터 넣어 둔 이유가 이것이다.

### 데이터 위치 — 반드시 확인할 것

베트남은 사이버보안법(Luật An ninh mạng 2018)과 시행령 53/2022/NĐ-CP로 **일정 서비스에 대해 국내 데이터 보관과 현지 법인 설립을 요구**한다. 정부 기관이 쓰는 시스템이라면 사실상 **베트남 국내 호스팅이 전제**라고 보는 것이 안전하다.

> **확인 필요**: 어느 사업자를 쓸 것인가(Viettel IDC · VNPT · FPT 등), 부처가 지정한 클라우드가 있는가.
> 이것은 법률 자문을 받아 확정해야 하며, 추정으로 진행하면 나중에 전체 이관이 필요해진다.

## 8. 데이터 이관

가장 과소평가되는 작업이다. 기존 자료는 대부분 **엑셀과 종이**에 있다.

| 단계 | 내용 |
|---|---|
| 1 | 기준 데이터 먼저 (34개 성/시, 종목 분류, 조직 목록) |
| 2 | 조직 → 사람 → 등록 순서 (참조 관계 때문에 순서가 고정) |
| 3 | 엑셀 템플릿 배포 → 협회가 채워서 회신 |
| 4 | 업로드 시 **검증 후 미리보기** → 확인 후 반영 |
| 5 | 중복 인물은 CCCD 해시로 탐지 |

> 종이만 있는 경우 OCR을 고려하되, **정확도가 낮으면 수기 입력이 더 빠르다.**
> 분량을 먼저 파악하고 결정한다.

## 10. 공식 시스템 지정을 위한 조건

목표가 **정부 공식 시스템 지정**이므로, 기능 외에 다음이 필요하다.

| # | 조건 | 비고 |
|---|---|---|
| 1 | **법적 근거** — 부처 결정문/통지문에 시스템 사용이 명시 | 이것이 있어야 협회가 의무적으로 쓴다 |
| 2 | 표준 서식의 공식 지정 | 하향식 강제의 근거 |
| 3 | 정보보안 심사 통과 | |
| 4 | 데이터 소유권·운영 주체 합의 | **누가 데이터를 소유하는가**는 초기에 못 박아야 한다 |
| 5 | 국내 호스팅 | §6 |
| 6 | 기존 정부 시스템과의 연동 | P1에서 확인 |
| 7 | 지속 운영 재원 | 유지보수 예산 확보 방식 |

> **4번이 가장 자주 분쟁이 된다.** 플랫폼 운영사와 부처 중 누가 데이터를 보유하는지,
> 계약 종료 시 어떻게 되는지를 문서로 정해두지 않으면 나중에 전체 사업이 흔들린다.

## 11. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| **서식이 계속 오지 않는다** | 전체 일정 지연 | 담당자 화면 사진이라도 확보(문서 08 §팁). 추정 서식으로 진행 후 교체 |
| **베트남에 이미 정부 시스템이 있다** | 설계 일부 폐기 | P1 첫 30분에 확인. 연동 설계로 전환 |
| 미팅에서 범위가 크게 늘어난다 | 일정·비용 증가 | 단계 분리. "1차 범위"를 문서로 합의 |
| 담당자 교체 | 합의 사항 초기화 | 모든 합의를 **문서로** 남기고 회의록 서명 |
| 현지 용어 오류 | 공문서 무효 | 원어민 검수를 개발과 **동시에** 진행 |
| 데이터 국내 보관 위반 | 법적 제재 | 법률 자문 후 호스팅 확정 |
| 협회의 저항 | 확산 실패 | 하향식 지정 + 교육 + 헬프데스크. 파일럿 성공 사례 활용 |
| 인력 이탈 | 개발 중단 | 문서화 유지(현재 docs 01~12), 테스트로 회귀 방지 |
