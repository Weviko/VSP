# 19. 배포 준비 — 베트남 리전 운영 전환 체크리스트

> 작성 2026-09-16 · 대상: IT팀·인프라 담당. 로컬 완성본(README 기준)을 **베트남 내** 운영 환경으로 올리는 절차.
> 원칙: 코드는 그대로, **환경(DB·저장소·비밀값·역할)만** 바꾼다. `DATABASE_URL` 한 줄 교체로 DB가 바뀌는 구조([README](../README.md)).

이 문서는 "무엇을 확인하고 어떤 순서로 올리나"만 다룬다. 개발 실행법은 README, 보안 설계 근거는 [문서 13](13-행정시스템-구조-비교.md)·[14](14-통합-플랫폼-설계.md)에 있다.

---

## A. 토폴로지 (무엇을 배포하나)

```
[대외 웹사이트 apps/portal]  ──(읽기, vsp_portal 역할)──┐
                                                         ├── PostgreSQL (베트남 리전)
[업무 플랫폼 apps/platform]  ──(읽기·쓰기, app 역할)────┘
        │
        └── 첨부 저장소 (S3 호환, 베트남 리전 버킷)
```

- 두 앱은 **같은 DB**를 본다. 대외 앱은 **최소권한(vsp_portal, pub 스키마 읽기만)**, 업무 앱은 일반 앱 역할.
- 두 앱은 서로를 링크로만 참조한다(`VSP_PORTAL_URL`/`VSP_PLATFORM_URL`) — 결합하지 않는다.

## B. 사전 준비 (베트남 내)

- [ ] **PostgreSQL 15+** (베트남 리전). 관리형이면 마이그레이션·역할 생성 권한 계정 확보.
- [ ] **S3 호환 오브젝트 스토리지** (베트남 리전) — 첨부·증빙. 버킷 1개.
- [ ] 앱 호스팅 2개(포털·플랫폼) 또는 1대에 포트 분리. Node 20+.
- [ ] 도메인 2개(예: `vsp.gov.vn` 포털, `admin.vsp.gov.vn` 플랫폼) + TLS.

## C. 데이터베이스 전환

1. [ ] DB 생성 후 마이그레이션·시드 적용:
   ```bash
   DATABASE_URL=postgresql://<app>:<pw>@<host>:5432/vsp npm run db:setup
   ```
   `db:setup`(--reset 없이)은 **미적용 마이그레이션만** 얹는다(멱등). 운영에서 `db:reset`(전체 삭제)은 쓰지 않는다.

2. [ ] **`vsp_portal` 역할 — 대외 앱 접속 계정.** 007 마이그레이션은 이 역할을 `NOLOGIN`으로 만든다.
   운영에서는 **로그인 가능한 접속 계정**이 필요하므로, 관리자(슈퍼유저/롤 생성 권한)로 아래를 1회 실행한다:
   ```sql
   -- 방법 A: 별도 로그인 계정에 vsp_portal 권한 부여(권장)
   CREATE ROLE vsp_portal_app LOGIN PASSWORD '<강한-비밀번호>';
   GRANT vsp_portal TO vsp_portal_app;
   -- 방법 B: 역할 자체에 로그인 부여
   -- ALTER ROLE vsp_portal LOGIN PASSWORD '<강한-비밀번호>';
   ```
   > 관리형 DB에서 마이그레이션 계정에 롤 생성 권한이 없으면 007이 역할 생성을 **건너뛴다**(NOTICE). 그때는 위 SQL을 관리자 콘솔에서 먼저 실행하고 `db:setup`을 다시 돌려 GRANT가 적용되게 한다.

3. [ ] **대외 앱 DB 접속을 vsp_portal 계정으로** 한다(포털의 `DATABASE_URL` = `vsp_portal_app` 접속 문자열). 업무 앱은 일반 앱 계정. → 대외 앱은 pub 뷰 외 어떤 원본도 읽지 못하는 것이 DB 권한으로 강제된다.

4. [ ] 검증: 포털 계정으로 `SELECT * FROM core.person LIMIT 1;` 이 **거부**되고, `SELECT * FROM pub.athlete LIMIT 1;` 은 되는지 확인. (`npm run test:public`이 로컬에서 같은 것을 검사)

## D. 저장소·환경변수

- [ ] `STORAGE_URL=s3://<버킷>` + S3 자격증명. 개발 `file://.storage` → 운영 S3.
- [ ] `.env`(커밋 금지). `AUTH_SECRET` **새로 생성**. `VSP_PORTAL_URL`/`VSP_PLATFORM_URL`을 실제 도메인으로.
- [ ] AI 추출기(선택): `VSP_LLM_API_KEY`/`VSP_LLM_MODEL` 주입 시 LLM 추출기로 자동 전환. 미주입이면 텍스트 기본 추출기(정상 동작). 어느 쪽이든 **사람 확정 후에만 결재 시작**.
- [ ] 비밀값은 명령·설정 파일에 평문으로 두지 않는다(시크릿 매니저/환경변수).

## D-2. 로그인 OTP 발송 (★ 운영 필수 ★)

로그인은 전화번호 + OTP 다. OTP 는 알림 어댑터(Zalo ZNS 우선, SMS 폴백)로 나간다.
**운영에서 어댑터가 없으면 `issueOtp` 가 `OTP_NOT_CONFIGURED` 로 실패한다 — 아무도 로그인하지 못한다.**
(개발에서는 어댑터가 없어도 화면에 dev code 가 떠서 진행된다. 이 dev code 는 운영에서 절대 나오지 않는다.)

- [ ] `ZALO_OA_TOKEN` 설정(Zalo OA 발송 토큰). 없으면 운영 로그인 불가.
- [ ] `ZALO_ZNS_TEMPLATES` 에 **`OTP_LOGIN` 템플릿 매핑 포함**. ZNS 는 사전 승인된 템플릿만 보낸다 — 매핑이 없으면 발송이 `OTP_SEND_FAILED` 로 실패한다.
- [ ] Zalo OA 콘솔에서 OTP_LOGIN 문안(`Mã đăng nhập VSP: {code}. Hiệu lực 5 phút…`)을 사전 승인받아 template_id 발급.
- [ ] 발송 사업자 계약 전이라면: SMS 폴백 어댑터 계약 여부 확인, 또는 미팅 전까지는 **개발 모드로만** 접근(운영 전환 시 위 항목 완료가 선행).
- [ ] 검증: 운영과 동일 설정(스테이징)에서 실제 번호로 코드 수신 → 로그인까지 1회 리허설.

> 남용 방지(코드에 내장, 설정 불필요): OTP 발급은 **번호별 5회/15분** + **IP별 20회/15분** 로 이중 제한한다. 한 곳에서 여러 번호로 스프레이해 SMS 비용을 태우거나 번호를 훑는 것을 막는다. 리버스 프록시가 실제 클라이언트 IP를 `X-Forwarded-For` 로 넘겨야 IP 제한이 동작한다.

> 비밀값 규칙: `ZALO_OA_TOKEN` 은 `.env`/시크릿 매니저로만 주입한다(명령·설정 평문 금지). 노출되면 삭제가 아니라 **재발급**한다.

## E. 빌드·배포

- [ ] `npm ci` → `npm run build`(플랫폼·포털). 빌드가 통과해야 배포한다.
- [ ] 두 앱을 각 호스트/포트로 기동, 리버스 프록시에서 도메인 매핑.
- [ ] 헬스체크: 두 앱 모두 `GET /api/health` (인증 불필요, DB 연결 확인 → 200 `{status:"ok",db:true}` / 실패 시 503). 로드밸런서·모니터가 이 경로를 친다. 화면 확인은 포털 홈(공개)·플랫폼 로그인 화면.

## F. 보안·법규 확인 (게이트)

- [ ] **데이터 현지화(시행령 53/2022)**: DB·첨부·백업이 모두 베트남 내.
- [ ] **개인정보(시행령 13/2023 PDPD)**: 신분증 원문 저장 금지(해시만) · 미성년 보호(출생연도만·동의 없으면 비공개) — 공개 규칙은 `007_public_views.sql` 한 곳에서 강제됨.
- [ ] **결제(시행령 52/2024)**: 플랫폼은 자금을 경유하지 않는다(돈은 납부자→PG→수취 조직 계좌로 직접). 결제 라이선스 필요 여부 법률 검토.
      결제 어댑터는 **골격만** 있다: VNPay 서명 생성/검증 + 리턴 확인(`confirmPaymentReturn`)이 테스트로 검증돼 있고(`test-payment`), 게이트웨이는 `.env`(VNPAY_*)로 등록된다. **공개 콜백 라우트 연결과 실제 가맹점 자격(조직별)은 라이선스·법률 검토 확정 후** 실무 통합에서 붙인다. 미설정 운영에선 게이트웨이를 등록하지 않아 모의로 대금이 확정되지 않는다.
- [ ] **전자서명 효력**: 전자결재의 법적 효력 근거 확인(국가 전자문서/서명 체계 연동 여부는 미팅 §B에서 확정).
- [ ] **베팅**: 공개·대외 문서·화면에 미언급(내부 문서 한정).
- [ ] `npm run check:boundaries` 통과(포털 import 제한·화면/액션 권한) — CI에 포함(`.github/workflows/ci.yml`: 타입체크→`npm test`(경계검사 포함)→빌드). 원격 저장소 연결 시 자동 실행된다.

## G. 성능·확장

- [ ] 조직 트리는 성/시 지부 포함 1,500+ 규모에서 검증됨(공개 뷰의 행별 집계 서브쿼리 제거, 화면은 상위 레벨+개수). 대량 데이터에서도 목록이 폭주하지 않는다.
- [ ] 커넥션 풀: 앱별 풀 크기와 DB `max_connections` 정합. 개발 `db:serve`는 최대 30.
- [ ] 인덱스는 마이그레이션에 포함(조직 parent/level/status, 사람 이름·신분해시, 등록·대회·구독·순위 등).

## H. Go-live 체크리스트

- [ ] DB 마이그레이션 적용 완료(미적용 0)
- [ ] vsp_portal 로그인 계정 생성 + 포털이 그 계정으로 접속
- [ ] 포털 계정 원본 테이블 접근 거부 확인
- [ ] **OTP 발송 어댑터 설정(Zalo ZNS·OTP_LOGIN 템플릿) + 실제 번호로 로그인 리허설** (미설정 시 로그인 불가)
- [ ] S3 저장소 연결·업로드/다운로드 확인
- [ ] AUTH_SECRET·도메인·교차 URL 설정
- [ ] 두 앱 빌드 통과·기동·헬스체크
- [ ] 백업 잡 등록(pg_dump + 버킷 스냅샷) — 복구 절차는 [README 백업·복구](../README.md)
- [ ] 감사원장(`core.audit_log`) 보존 정책 설정(삭제 금지)

## I. 롤백

- 마이그레이션은 전방(forward)만 둔다. 문제 시 **이전 스냅샷으로 복구**(pg_restore + 버킷 스냅샷)한다.
- 앱은 이전 빌드로 되돌린다. DB 스키마 변경과 앱 배포는 **순서**를 지킨다(스키마 먼저, 하위호환 유지).

---

**요약**: 운영 전환의 급소는 (1) DB `DATABASE_URL` 교체 + 마이그레이션, (2) **vsp_portal 로그인 계정**으로 대외 앱 최소권한 접속, (3) **로그인 OTP 발송 어댑터(Zalo ZNS·OTP_LOGIN)** — 없으면 아무도 로그인 못 한다, (4) 저장소 S3·비밀값, (5) 데이터 현지화·개인정보·결제 법규 게이트. 코드는 바꾸지 않는다(설정만).
